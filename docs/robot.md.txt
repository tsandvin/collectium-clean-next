# Collectium UI/UX 8.6 — Robotregler for visningskort, objektpresentasjon, relasjonsside, index og periodefilter

## 1. Formål

Denne filen er en robot-/AI-instruksjonsfil for Collectium UI/UX 8.6.

Den skal brukes av:

```text
AI
Codex
Antigravity
utvikler
designsystem
sandbox
kontrollside
automatiske kodeverktøy
```

Formålet er å sikre at Collectium bygges som én samlet relasjonsplattform, ikke som løse sider, løse kort eller tilfeldige React-komponenter.

Denne filen definerer:

```text
hva UI/UX 8.6 skal vise
hvordan visningskort skal oppføre seg
hvordan objektpresentasjon skal fungere
hvordan relasjonssider skal fungere
hvordan index skal bruke periodefilter
hvordan Filter Master binder sidene sammen
hvordan tilgang, medlemskap og datapakker skal vises
hvordan auksjon, nettbutikk, forhandler og samling skal kobles til objektet
hva AI/robot aldri skal hardkode
```

Dette er ikke en vanlig `robots.txt` for søkemotorer.

Dette er en intern Collectium robotregel for bygging, kontroll og videreutvikling av UI/UX 8.6.

---

## 2. Hovedskille mellom UI/UX 8.6 og DB Neon 8.6

Collectium 8.6 skal deles i to standarder:

```text
UI/UX 8.6
= hva brukeren ser, gjør, forstår og kan trykke på

DB Neon 8.6
= hvor data ligger, hvordan data hentes, hvilke API-ruter, feature_keys, access_rules, tabeller, views og logger som styrer sannheten
```

UI/UX 8.6 skal aldri eie sannheten.

DB Neon 8.6 skal eie sannheten.

UI/UX 8.6 skal bare vise data, handlinger, relasjoner, filterverdier, medlemskap og status som kommer fra API/server actions og DB Neon 8.6.

Riktig dataflyt:

```text
DB Neon 8.6
→ API / server action
→ Next.js
→ React-komponent
→ UI/UX 8.6
```

Ikke:

```text
React
→ hardkodede objekter
→ hardkodede relasjoner
→ hardkodede priser
→ hardkodede filterverdier
→ hardkodede tilgangsregler
```


## 4. Grunnmodell for objekt, visningskort, objektpresentasjon, relasjonsside og index

Alle objekter skal følge samme hovedmodell:

```text
Objekt
→ visningskort
→ objektpresentasjon
→ relasjonsside
→ index / periodeanalyse
→ tilbake til filtrert katalog
```

Dette betyr:

```text
Visningskort
= kort inngang til objektet

Objektpresentasjon
= full presentasjon av ett objekt

Relasjonsside
= kunnskapsside for én relasjonsnode

Index
= analyse-, marked- og periodeflate

Periodefilter
= tidsmotoren som binder alt sammen

Filter Master
= felles filterkontrakt for hele plattformen
```

Ingen del skal bygges som et isolert system.

## 5. Låst hovedregel for UI/UX 8.6

```text
Ingen katalog uten Filter Master.
Ingen visningskort uten direkte lenke til objektpresentasjon.
Ingen visningskort uten relasjonskobling.
Ingen objektpresentasjon uten periode- og relasjonskobling.
Ingen objektpresentasjon uten tilgangsstyrt visning basert på medlemsnivå.
Ingen relasjonsside uten periodekontekst.
Ingen index uten periodefilter.
Ingen auksjon uten objektkobling.
Ingen nettbutikk uten objektkobling.
Ingen forhandlerside uten objekt-, prosess- og filterkobling.
Ingen samling uten objekt-, periode- og filterkobling.
Ingen knapp uten feature_key, action_route eller tydelig lokal UI-funksjon.
```

Alle brukere må være pålogget for å kunne gi bud.

Budgivning krever medlemskap og tilgangsregel som åpner objektpresentasjon, relasjonsside og nødvendig periode-/objektinformasjon.

## 6. Objekt som hovedmodul

Objekt er kjernen i Collectium.

Et objekt kan vises i:

```text
katalog
visningskort
objektpresentasjon
relasjonsside
index
min samling
ønskeliste
favoritter
auksjon
nettbutikk
forhandlerflate
admin
```

Alle objekter skal identifiseres med:

```text
object_id + object_group + source_key
```

Eksempel:

```text

object_group = banknote
object_id = 1459
```

Robot skal aldri bruke bare `id` som objektidentitet.

## 14b. Rad 2 og Rad 3 dropdown / brytere

### Dynamiske innholdsfelt for brytere og segmenter

Tidslinjen skal ikke bare flytte blokker visuelt. Den skal også fylle de dynamiske innholdsområdene under tidslinjen basert på:

1. valgt Rad 1-bryter
2. valgt Rad 2-bryter
3. valgt Rad 3-bryter
4. valgt segment: Samler / Historie / Finans
5. valgt node/blokk i tidslinjen

Det skal finnes en felles datamodell for dynamisk innhold, slik at UI ikke hardkoder tekstene (`type Period86DynamicContent`).

### Dynamisk område 1: Historisk sammenheng

Venstre dynamiske område under tidslinjen skal endre innhold etter valgt segment og brytere (Samlersammenheng, Historisk sammenheng, Finansiell sammenheng).
Dette området skal forklare hvorfor de valgte radene sammenlignes.

### Dynamisk område 2: Valgt tidslinjeinnhold

Høyre dynamiske område under tidslinjen skal vise valgt blokk/node. Når bruker klikker på en tidslinjeblokk, skal dette området fylles med innhold fra valgt node (navn, typegruppe, fra-til år, kort sammendrag, historisk kontekst, samlerrelevans, finansrelevans, relation_href).

### Segmentregler: Samler / Historie / Finans

Segmentet skal styre hvilke innholdsfelt som prioriteres, ikke endre selve årsskalaen.
- Samler: objekt-/utgiverperiode, samlerobjekter, sjeldenhet, samlingsrelevans, osv.
- Historie: historisk kontekst, regent, krig/konflikt, hendelser, styreform.
- Finans: finans/økonomi, pengehistorie, inflasjon, kriser, verdiutvikling.

### Brytervalg skal ha egne beskrivelser

Dropdown-verdier (switch options) for Rad 1, Rad 2 og Rad 3 skal defineres som `Period86SwitchOption` med key, label_no, description_no, row_key og preferred_segment.

### Klikk og valgt node

Når bruker klikker på en tidslinjeblokk:
- sett `selectedNode`
- sett `selectedLane`
- sett `selectedSegment`
- oppdater dynamisk område 2
- oppdater dynamisk område 1 med sammenheng mellom valgte rader
Hvis ingen blokk er valgt, skal dynamisk område 2 vise en oppsummering av valgt kombinasjon av brytere.

### Fallback for dynamisk innhold

Hvis API ikke returnerer ferdig dynamisk tekst, skal frontend bygge nøktern fallback fra nodefeltene (`label_no`, `type_group_label_no`, `start_year`, `end_year`, `relation_href`). Fallback skal være faktabasert og kort. Ikke finn opp historisk innhold i frontend.

### Ekstra krav

Dynamisk område 1 og Dynamisk område 2 skal ikke være statisk tekst. De skal reagere på brytervalg, segmentvalg og valgt tidslinjeblokk. Samler, Historie og Finans skal prioritere ulike innholdsfelt, men de skal aldri endre den felles årsskalaen.

## 19. Visningskort — handlinger

Visningskort skal ha tre hovedhandlinger:

```text
Åpne objekt
Relasjoner
Legg i samling
```

### Åpne objekt

Åpner full objektpresentasjon.

URL:

```text
/objekt/[sourceKey]/[objectGroup]/[objectId]
```

Eksempel:

```text
/objekt/norske_sedler/banknote/1459
```

### Relasjoner

Relasjoner skal ikke være en løs knapp.

Relasjoner skal åpne en popup, meny eller liste med objektets faktiske relasjoner.

Eksempel:

```text
År · 1877
Regent · Oscar II
Signatur · Winge / Getz
Motiv · Riksvåpen
Utgave · 1. utgave
Kilde · Norske sedler
Valør · 100 kroner
Produsent · Norges Bank
```

Hver relasjon skal være klikkbar og åpne relasjonspresentasjon.

### Legg i samling

Skal kobles til brukerens samling og brukerstatus.

Dette skal ikke være lokal frontend-state alene.

## 53. Endelig låst modell

```text
Visningskort
= kompakt objektinngang
= viser objekt, verdi, år, periode og raske relasjoner
= åpner objekt, relasjon eller samlingshandling

Objektpresentasjon
= full visning av ett objekt
= viser Samler, Historie og Finans
= bruker periode og relasjon som kontekst
= tilgangsstyrt etter medlemskap og rolle

Relasjonsside
= kunnskapsside for én node
= viser objekter, periode, historikk, marked og videre relasjoner
= har fane for relasjon til andre samleobjekter

Index
= analyse- og markedsmotor
= eier bred periodeanalyse og utvikling over tid
= bruker Filter Master og periodefilter

Periodefilter
= felles tidsmotor
= brukes på katalog, objekt, relasjon, index, auksjon, nettbutikk, forhandler og samling

Filter Master
= felles filterkontrakt
= hindrer at hver side lager sin egen filterlogikk

DB Neon 8.6
= sannhet for data, tilgang, relasjoner, filter, action routes, logging og kontroll

UI/UX 8.6
= viser riktig informasjon, riktig handling og riktig forklaring til bruker
```

## 54. Kort låsbar formulering

Collectium UI/UX 8.6 skal bygges slik at visningskort, objektpresentasjon, relasjonsside, index, auksjon, nettbutikk, forhandler og samling deler samme Filter Master og periodefilter. Visningskortet viser kort objektkontekst, objektpresentasjonen forklarer ett objekt, relasjonssiden forklarer én relasjonsnode, og index analyserer utvikling på tvers av perioder, marked, relasjoner og objekter. Frontend skal ikke finne opp relasjoner, perioder, priser, filterverdier, medlemskap eller fakturaflyt. API/DB Neon 8.6 skal levere nøkler, href-er, tilgang, status, datagrunnlag og logging.
